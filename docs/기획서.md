# 우리의 마블 포지 기획서

> 원본 [Our-Marble/our-marble-client](https://github.com/Our-Marble/our-marble-client)를 포크해서, **별도 서버 없이 방장이 게임 규칙을 돌리는 멀티플레이**(Photon Fusion Shared 모드)로 바꾸는 프로젝트입니다.

**현재 상태:** v1.0 배포 완료 (봇과 함께 혼자 플레이). 다음은 Photon 적용입니다. ([게임 페이지](https://vmffpdlwnd35.itch.io/our-marble))

## 1. 한 줄 요약

"모두의 마블"을 모티브로 한 2~4인 온라인 보드게임을, **게임 파일 하나만 켜면 친구와 바로 할 수 있게** 만든다.

## 2. 목표와 범위

### 목표
- 서버 프로그램, Redis, 로그인 없이 방장이 방을 만들고 친구가 들어오는 멀티
- 원본의 화면·연출·규칙은 최대한 그대로 유지
- 무료 범위(Photon Fusion 무료 100 CCU) 안에서 운영

### 포함
- 타이틀, 로비(방 목록), 대기방(준비, 방 설정), 인게임, 결과 화면
- 주사위 이동, 땅 구매·건설·통행료·인수·매각·파산
- 월급, 세무조사, 적립금, 황금열쇠, 세계여행, 무인도, 3연속 더블
- 봇 (기본형)
- 재접속 (연결이 끊긴 사람이 같은 브라우저로 다시 들어오면 현재 상태로 복구)
- 방장 승계 (방장이 나가면 입장 순서대로 다음 사람이 방장이 되고 게임을 이어감)

### 제외
- Java 서버, Redis, JWT 로그인·회원가입, 전적 DB
- 방장을 직접 다른 사람에게 넘기는 기능 (Shared 모드에서는 방장이 나갈 때만 바뀐다)

### 후순위
- 성향별 봇: 기본형을 먼저 만들고, 나머지는 나중에
- 파산 신청과 포기 기능: 플레이어가 스스로 파산을 선언하거나 게임을 포기하는 기능. 돈이 모자라 자동으로 파산하는 처리는 포함
- 황금열쇠 종류 추가
- 초기 컨셉 스테이지: 지명 대신 가상의 프랜차이즈를 쓰는 새 보드 (새 보드와 땅 데이터가 필요)
- 로비에서 코드로 입장
- 선턴 결정 방식: Photon 연결 후 결정. (원본은 무작위 없이 방 참가 순서대로 시작하고 방장이 첫 차례. 지금 코드는 무작위)

## 3. 원본과 달라지는 점

| 항목 | 원본 | 이 프로젝트 |
| --- | --- | --- |
| 구조 | 전용 서버(Java/Spring)가 모든 판정 | **방장(마스터 클라이언트)이 판정** |
| 멀티 기술 | WebSocket 직접 구현 | **Photon Fusion** (Shared 모드) |
| 서버 실행 | 별도 서버 필요 | 게임 하나만 실행 |
| 로그인 | JWT, 이메일 인증 | 닉네임만 입력 |
| 방 저장소 | Redis | Fusion 세션 |
| 규칙 코드 | Java 서버 | **C#으로 복귀** (원래 Unity에 있던 코드 + 서버 명세 기준) |
| 봇 | 서버에서 실행 | 방장에서 실행 |
| 전적 | 서버 DB | 제외 (필요하면 로컬 저장) |

## 4. 기술 스택

| 영역 | 기술 |
| --- | --- |
| 엔진 | Unity 6 (6000.3), C#, URP 2D |
| 멀티 | Photon Fusion (Shared 모드) |
| UI | uGUI, TextMesh Pro |
| 연출 | DOTween |
| 직렬화 | Newtonsoft.Json |
| 데이터 | ScriptableObject (보드·카드), JSON (땅 가격표) |

### 웹(WebGL)과 Shared 모드
- 웹에서는 Photon이 **Shared 모드를 권장**한다. Host 모드는 WebGL에서 기본으로 꺼져 있고, 연결이 자주 끊기고 항상 중계 연결을 쓴다고 공식 문서에 적혀 있다.
- 브라우저는 스레드가 하나라서, 방장 브라우저가 호스트 서버 역할을 하는 방식(Host 모드)은 부담이 크다. 그래서 Shared 모드를 쓴다.

### Photon 무료 한도
- 무료 100 CCU는 **Fusion/Quantum 전용, 계정당 앱 하나**
- CCU는 방 단위가 아니라 전체 동시접속자 수. 방당 4명이면 약 25방
- 앱 ID를 여러 개 만들어 한도를 합치는 방식은 쓰지 않는다
- 가격 정책은 바뀔 수 있으므로 실제 사용 전에 Photon 대시보드에서 확인

## 5. 구조

### 호스트 권위 방식 (Shared 모드)
- Photon Shared 모드에는 서버도 호스트 플레이어도 없다. 대신 방마다 **마스터 클라이언트** 한 명이 정해진다. 우리는 마스터를 방장으로 쓰고, 게임 규칙 판정, 봇, 시간을 맡기는 이 역할을 이 문서에서 **호스트**라고 부른다.
- 마스터는 방을 만든 사람이 처음 맡고, 나가면 **들어온 순서대로 가장 오래 남은 사람**이 맡는다. 마스터를 직접 지정할 수는 없다.
- 방장 클라가 주사위, 구매 검증, 통행료, 턴 진행을 처리하고 결과를 전원에게 보낸다.
- 참가자는 "주사위 굴릴게요", "구매할게요" 같은 **요청만 보내고 결과만 받는다.**
- 서버 시절의 "요청 → 검증 → 결과 알림" 흐름을 그대로 유지한다.

### 요청 (참가자 → 방장)

| 요청 | 내용 | 허용 단계 |
| --- | --- | --- |
| 주사위 굴리기 | 없음 | 굴리기 대기 |
| 세계여행 목적지 | 목적지 칸 번호 | 목적지 대기 |
| 황금열쇠 뽑기 | 없음 | 카드 대기 |
| 땅 구매·거절 | 땅 번호, 수락 여부 | 구매 대기 |
| 건설·거절 | 땅 번호, 수락 여부 | 건설 대기 |
| 인수·거절 | 땅 번호, 수락 여부 | 인수 대기 |
| 매각 | 팔 땅 번호 목록 | 매각 대기 |
| 상태 요청 (재접속) | 없음 | 제한 없음 |

### 알림 (방장 → 전원)

주사위 결과, 목적지 선택, 카드 결과, 구매·건설·인수 결과, 매각 결과, 상태 동기화(재접속자에게만).

Photon 호출(RPC) 하나는 약 512바이트까지라서, 방 정보와 상태 동기화처럼 큰 메시지는 큰 데이터 전송으로 보낸다. (설치할 SDK 버전에서 지원을 확인한다)

### 클라가 같은 규칙으로 계산하는 처리
통행료, 월급, 파산, 세무조사, 적립금, 무인도, 3연속 더블, 턴 전환, 황금열쇠 효과는 알림 없이 **호스트 판정과 같은 규칙**으로 각 클라가 반영한다. 규칙을 바꿀 때는 호스트와 참가자 코드를 같이 고친다. (호스트와 참가자는 공용 `Rules/` 코드를 쓴다)

### 검증 순서 (방장이 요청을 받을 때)
1. 진행 중인 게임이 있는가
2. 땅 번호가 있다면 존재하는 땅인가
3. 요청자의 차례인가
4. 파산하지 않았는가
5. 요청이 현재 단계에 맞는가
6. 제한 시간 안인가
7. (구매·건설·인수) 요청자의 말이 그 땅 위에 있는가
8. 기능별 검증 (현금, 소유자, 건설 가능 여부 등)

검증이 하나라도 실패하면 상태는 바뀌지 않고 요청자에게만 오류를 보낸다.

### 사람 구분과 재접속
- 한 판 동안 사람은 **연결마다 Photon이 붙이는 번호**(`PlayerRef`)로 구분한다. 요청에서 "누가 보냈는지"는 Photon이 알려 주는 연결로 정하고, 메시지 안에 클라이언트가 적은 번호는 믿지 않는다. 닉네임은 구분에 쓰지 않아서 같은 이름이 둘 들어와도 된다.
- 연결이 끊겼다 다시 들어오면 새 번호가 붙는다. Shared 모드에서는 `ConnectionToken`을 쓸 수 없어서, **브라우저가 처음 만들어 저장해 둔 고유 값**을 방장에게 보내 이전 자리를 알아보게 한다.
- 이 방식은 **같은 브라우저에서만** 알아본다. 브라우저 저장 데이터를 지우거나 다른 기기로 들어오면 새 사람으로 취급한다. (계정이 없기 때문)

### 방장 승계
- 방장이 나가면 다음 사람이 마스터가 되고 호스트 역할(규칙 판정, 봇, 시간)을 이어받는다. 방은 끝나지 않는다.
- 모든 클라이언트가 같은 규칙으로 게임 상태를 따로 계산해 가지고 있어서, 새 방장은 **자기 상태로 호스트를 시작**한다.
- 호스트만 알던 값(제한 시간이 얼마나 흘렀는지, AFK 표시, 처리 중이던 요청)을 어떻게 이어받을지는 8단계에서 정한다.

## 6. 게임 규칙

### 기본 설정

방장이 대기방에서 바꿀 수 있는 값은 인원, 봇 수, 초기 자금, 최대 라운드, 월급 다섯 가지다. 나머지는 고정이다.

| 항목 | 기본값 | 방장 변경 |
| --- | --- | --- |
| 인원 | 2~4명 (사람 + 봇) | 가능. 봇 수와 사람 수의 합이 인원을 넘을 수 없다 |
| 초기 자금 | 1,000,000 | 가능 (200,000 / 300,000 / 500,000 / 1,000,000 / 2,000,000) |
| 월급 | 150,000 | 가능 (50,000 / 100,000 / 150,000 / 200,000 / 300,000) |
| 최대 라운드 | 20 | 가능 (10 / 15 / 20 / 30 / 40) |
| 세무조사 세금 | 100,000 | 고정 |
| 무인도 영업정지 | 3턴 | 고정 |
| 입력 제한 시간 | 60초 | 고정 |
| 보드 | 32칸, 땅 23개 | 고정 |

### 경제 규칙

| 항목 | 규칙 |
| --- | --- |
| 투자금 | 땅값 + 지금 단계까지 지은 건물 비용 |
| 매각가 | 투자금 × 50% |
| 인수가 | 투자금 × 200% |
| 통행료 | 땅 단계별 값 (땅, 별장, 빌딩, 호텔). 주인이 없으면 0 |
| 건설비 | 올라갈 단계 한 번의 비용 (누적 아님) |
| 총자산 | 현금 + 가진 땅의 투자금 합계 |
| 월급 | 출발 지점을 지나거나 도착하면 지급. 세계여행 이동 중 통과도 지급. 무인도 이동과 뒤로 가는 카드는 지급 안 함 |
| 세무조사 | 현금 한도 안에서만 걷고, 걷은 금액은 적립금에 쌓임 |
| 적립금 | 적립금 칸 도착 시 쌓인 금액 전액 지급 |

- 금액 계산은 **정수 연산**으로 한다. (원본 C#의 `long × 0.5f`는 정밀도 한계가 있음)
- 인수 후에도 건물 단계는 유지되고 주인만 바뀐다.

### 통행료 흐름
1. 현금 ≥ 통행료: 주인에게 이체. 이체 후 현금 ≥ 인수가면 인수 선택, 아니면 턴 종료
2. 현금 < 통행료이고 현금 + 전체 매각가 ≥ 통행료: 매각 선택 후 이체, 턴 종료 (매각 뒤 인수 선택 없음)
3. 전부 팔아도 모자라면 파산: 땅을 매각가로 현금화해 전액을 땅 주인에게 넘기고, 땅은 주인 없음 + 땅 단계로 초기화. 더블이어도 다음 플레이어로 넘어간다.

### 특수 칸과 규칙

| 항목 | 규칙 |
| --- | --- |
| 무인도 | 도착하면 영업정지 3턴, 턴 강제 종료. 영업정지 중 더블이 아니면 남은 턴 -1하고 이동 없이 종료. 더블이면 해제되고 그 더블로 이동 (추가 턴 없음). **남은 턴이 0이 된 뒤 더블은 일반 더블로 처리** (서버 이식 때 고친 버그) |
| 3연속 더블 | 3번째 더블이면 이동 없이 무인도로 (월급 없음) |
| 세계여행 | 다음 턴이 목적지 선택으로 시작. 세계여행 칸 자체는 목적지로 고를 수 없음. 도착 후 더블이어도 턴 넘김 |
| 건설 불가 땅 | 독도 등 관광지는 건설 없이 땅 기준 통행료 |
| 황금열쇠 | 보너스, 벌금, 지정 칸 이동, N칸 이동, 무인도. 카드는 매번 전체 중 무작위 |

### 턴 단계
굴리기 대기 → (도착 칸에 따라) 구매 / 건설 / 인수 / 매각 / 카드 / 목적지 대기 → 턴 종료. 요청 하나가 흐름을 끝까지 처리한 뒤 끝난 단계만 저장한다.

### 게임 종료와 등수
- 종료: 생존자 1명 이하이거나, 다음 라운드가 최대 라운드를 넘을 때
- 파산한 사람의 등수는 파산 시점의 생존자 수 (4명 중 첫 파산 → 4위)
- 생존자는 총자산 → 현금 → 원래 턴 순서로 등수 부여

## 7. 입력 제한 시간, AFK, 봇

- 사람 차례는 제한 시간(기본 60초) 안에 입력이 없으면 호스트가 대신 진행하고 AFK로 표시한다.
- 봇 차례는 6초 뒤 호스트가 진행한다.
- AFK인 사람은 다음부터 8초만 기다리고 대신 진행한다. 요청을 보내거나 재접속하면 AFK가 풀린다.
- 화면의 선택창은 호스트의 대기 시간보다 먼저 닫힌다. (일반: 화면 50초 / 호스트 60초, AFK: 화면 5초 / 호스트 8초) 호스트가 먼저 움직이면 화면과 겹쳐 입력이 거절되므로 이 순서를 유지한다. 그 사이 10초와 3초는 연출이 늦어지는 시간과 네트워크 지연을 덮는 여유다.
- 시간 값(봇 6초, AFK 8초, 화면 여유 10초와 3초)은 코드의 `TimeRules` 한 곳에서 정하고, 호스트와 화면이 같은 값을 쓴다.
- 대신 진행(제한 시간 초과, AFK)과 봇은 **같은 전략**이 구매·건설·인수·매각·세계여행 목적지를 판단하고, **사람과 같은 처리 함수**를 호출한다. 거절도 반드시 같은 경로로 호출해야 턴이 멈추지 않는다.
- 봇 판단: 구매·건설·인수는 ① 통행료 위험 → ② 가치 판단 → ③ 기회비용을 모두 통과해야 진행. 매각과 세계여행 목적지도 전략이 고른다. (판단 기준값은 `BotSettings`로 분리)

## 8. 화면 흐름

타이틀 → 로비 → 대기방 → 인게임 → 결과 화면 → 같은 방 대기 상태로 복귀

| 화면 | 내용 |
| --- | --- |
| 타이틀 | 닉네임 입력, 시작 |
| 로비 | 방 목록(새로고침), 방 만들기, 입장 |
| 대기방 | 준비, 방장 설정(초기 자금, 월급, 라운드, 인원, 봇 수), 채팅. 방장이 나가면 다음 입장자가 방장이 되어 설정과 시작 권한을 이어받는다 |
| 인게임 | 주사위·말 이동, 구매·건설·인수·매각 팝업, 세계여행 선택, 카드, 턴 타이머 |
| 결과 | 등수 표시 후 같은 멤버로 대기방 복귀 |

## 10. 위험 요소

| 위험 | 대응 |
| --- | --- |
| 방장이 나가면 게임이 멈춤 | Shared 모드의 마스터 자동 승계(입장 순서)를 쓰고, 새 방장이 자기 상태로 호스트 역할을 이어받는다. 호스트만 알던 값을 맞추는 방법은 8단계에서 정한다 |
| 방장 브라우저 탭이 뒤로 가면 자동 진행이 늦어짐 | 브라우저가 뒤로 간 탭의 업데이트를 줄이므로, 방장은 게임 탭을 앞에 두도록 안내한다 |
| 재접속 때 같은 사람인지 알 수 없음 | 브라우저가 만든 고유 값으로 확인한다. 브라우저 저장 데이터를 지우거나 다른 기기에서는 새 사람이 된다 |
| 큰 메시지가 Photon 호출 한도(약 512바이트)를 넘음 | 큰 데이터 전송을 쓴다. 6단계에서 설치할 버전의 지원을 확인한다 |
| 방장이 직접 조작하면 치팅 가능 | 친구끼리 하는 용도라 허용. 배포 범위를 넓힐 때 다시 검토 |
| 호스트와 참가자의 규칙 계산이 어긋남 | 규칙을 `Rules/`로 모아 호스트와 클라가 같은 코드를 쓴다. 개발 중에는 상태 비교 로그(`HostStateCheck`)로 어긋남을 잡는다 |
| 서버 이식 때 고친 버그가 되돌아옴 | 이 문서의 규칙표와 원본 서버 구현을 기준으로 직접 플레이해 확인하고, 호스트와 클라 상태 비교 로그로 어긋남을 잡음 |
| 무료 한도 초과 | 100 CCU면 약 25방. 한도에 닿으면 접속이 막히므로 대시보드에서 확인 |
| 원본 라이선스 | 원본 레포에 라이선스 파일은 없지만, 원작 팀이 사용에 문제없다고 확인함 (공개 배포 완료) |
